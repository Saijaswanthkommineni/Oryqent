## 1. Validator rules (source: `backend/config/settings/production.py`, lines ~35–45)

The request named `backend/config/settings/base.py`. That file only reads `DJANGO_SECRET_KEY` from the environment and falls back to a random dev key outside production. The production check lives in `production.py`. It rejects the key unless all of these hold:

- Length is at least 50 characters.
- At least 5 distinct characters.
- Does not start with `django-insecure-` (case-insensitive).
- Does not contain `replace-with`, `change-me`, or `changeme` (case-insensitive; `_PLACEHOLDER_MARKERS`, line 23).

No other rules apply to the key.

**Secret handling checks:**
- The generated value reaches the `Django deployment checks` step through `$GITHUB_ENV`. That step does not repeat the key in its `env:`.
- `backend-postgres` uses a CI-only static string. It is not a production or developer credential and is not a placeholder marker.
- The generated value is never echoed. It is written only to `$GITHUB_ENV`. No artifact upload includes `$GITHUB_ENV` or the job environment; uploads are limited to `backend-postgres-evidence`.
- `DJANGO_SECRET_KEY` is not printed, and no step runs with `set -x`.

**Neither job needed a change.** Both credentials satisfy the validator, so no workflow files were edited in this sprint.
